## Brief

**Claim.** You give a team of agents one goal in plain words; Personas splits it into steps,
gives each step to the right persona, runs the independent ones at the same time, and sends
a failed PR back to the builder until QA passes it and the mission lands.

**Five-second answer.** "You type one goal like 'Add CSV export to Reports'; Personas splits it
into steps for Solution Architect, Dev Clone, Code Reviewer and QA Guardian, runs review and
testing side by side, and when QA Guardian requests changes Dev Clone fixes the PR (round 2)
before the mission lands."

steps running at the same time, a real bounce-and-fix, and a terminal "Landed".

**Process or state.** Process (order, parallel, loop). Needs a time axis or beat list; the
product-true variant shows the state it leaves behind.

**Real artifact.** Goals -> Missions (`GoalsMissions.tsx`): phase rail on the left, focused

## The three

Default triad: mechanism (relay), product-true (missions), spatial (roster).
- **Relay** answers "how does it run?" - order, parallel, the bounce.
- **Missions** answers "what will I see?" - the real screen, fewer rows.
- **Roster** answers "who does the work?" - one goal matched to some of the team, not all.

### Variant `relay` - Step graph (mechanism)

- Section copy. Heading: **From goal to shipped**. Lede: "Give your agent team one goal.
  Personas splits it into steps, runs independent ones side by side, and when QA Guardian
  sends a PR back, Dev Clone fixes it before the mission lands."
- Label plan (words inside the art): goal card "Add CSV export to Reports" (5); node Scope
  "Scope" + "Solution Architect" (3); node Build "Build PR" + "Dev Clone" (4); node Review
  "Review" + "Code Reviewer" (3); node Test "Test PR" + "QA Guardian" (4); badge on Test
  "round 2" (2); loop arrow "changes requested" (2); bracket over the stacked pair "in
  parallel" (2); end chip "Landed" + "PR merged" (3). Total 28, longest run 5.
- Visual structure: a left-to-right DAG of five cards and an end chip, with a two-card column
  (parallel, F2/F7) and a dashed amber loop from Test back to Build (F3), ending in a green
  Landed chip (F5). Mute test: fork, stacked pair, loop-back and the green end read as shape.
- Size plan: viewBox 1000 x 360 (six columns at ~165px, cards 150 x 64, two text lines at
  17/14 units). Aspect 2.78. Max width 1180px; below that it follows the slot height.
  Phone: a tall 360 x 640 layout (top to bottom), same labels.
- Motion (mechanism, one progress value, plays once in view, replay button):
  1. 0.00-0.14 goal -> Scope edge lights, Scope turns done;
  2. 0.14-0.30 Build PR runs, done;
  3. 0.30-0.46 Review and Test PR light together (parallel);
  4. 0.46-0.60 Test flashes rose, the loop arrow lights back to Build, Build re-runs,
     "round 2" pops;
  5. 0.60-0.82 Test PR passes;
  6. 0.82-1.00 Landed lights.
- Degraded: server / reduced motion = p 1 (every card done, loop drawn with its label and
  arrowheads, round 2 badge, Landed lit): the still carries direction marks.

### Variant `missions` - Missions view (product-true)

- Section copy. Heading: **From goal to shipped**. Lede: "Every goal becomes a mission you can
  watch: its steps, the agent on each one, and where it stands. A PR that QA sends back shows
  its round; the mission lands when every step is done."
- Label plan (as built): rail headers "Active", "Needs review", "Landed" (4); rail rows
  "Weekly digest", "Billing migration", "CSV export" (6); focused header "Add CSV export to
  Reports" (5) + status "Landed" (1); step rows (title + persona chip) "Scope" / "Solution
  Architect", "Build PR" / "Dev Clone", "Review" / "Code Reviewer", "Test PR" / "QA Guardian"
  (14); badge "round 2" (2). Total 32. Status shown by the app's own icons and colours
  (check = Done, loader = Running, cross = Failed); persona chips carry an icon, as the app's
  PersonaIcon does; the header carries the app's persona stack. The CSV mission moves from
  Active to Landed in the rail when its last step lands.
- Visual structure: the real two-pane Missions layout, reduced to two missions and four steps.
  Mute test: a rail of grouped rows and a numbered vertical relay with one amber badge.
- Size plan: DOM, 880 x ~330 at base (four 52px rows), `data-stage-zoom` for tall screens.
  Phone: the rail hides; the relay stays.
- Motion (reveal, product-true): statuses advance as the app polls them - rows 1-2 Running
  then Done, rows 3-4 Running together, row 4 bounces to amber, row 2 re-runs, "round 2"
  appears, row 4 Done, header Running -> Landed. End frame says everything.
- Degraded: server / reduced motion = final state.

### Variant `roster` - Team roster (spatial)

- Section copy. Heading: **From goal to shipped**. Lede: "Type one goal for the team. Sonnet
  splits it into steps and hands each to the member who fits; the rest stay free, and the
  mission lands when every step is done."
- Label plan: goal bar "Add CSV export to Reports" (5); splitter "Sonnet" (1); step chips
  "Scope", "Build", "Review", "Test" (4); roster members "Solution Architect", "Dev Clone",
  "Code Reviewer", "QA Guardian", "Docs Steward", "Security Sentinel" (12); end chip "Landed"
  + "PR merged" (3). Total 25.
- Visual structure: fan-out, match, fan-in: goal -> splitter -> four routes to four of six
  roster cards (two dim, unrouted) -> four lines converge on Landed. Mute test: one to many to
  one, with two members left unlit.
- Size plan: viewBox 1000 x 380, aspect 2.63, max 1180px. Phone: tall 360 x 660 layout.
- Motion (mechanism): goal -> split (chips appear at the splitter) -> chips travel to their
  members (Scope first, Build next, Review and Test together) -> members light -> converge
  lines light -> Landed.
- Degraded: final state: every route drawn, chips docked on their members, Landed lit.
