# Personas (fleet monitor)
> The dashboard's main view: every persona in the fleet on one screen, in two views over the same synthetic fleet of up to 99 agents in nine teams: the **Board** (the remote management center for the PC the agents run on: team bays or a sortable list, drill-down to team and agent console, remote commands, triage, search, command palette, activity log) and **Night shift** (the fleet as a city, kept as a showcase without drill-down) · **Route:** `/dashboard/personas` (`/dashboard`, `/dashboard/agents` and `/dashboard/playground` redirect here) · **Nav:** first rail item, "Personas" · **Status:** Desktop stage demo-only (synthetic demo fleet); phone layout on demo + the live sync plane

## What it does
One page answers *is everything fine, who needs me, what is moving, where do I go next* two ways over the same synthetic fleet of 99 agents in nine teams. A thin toolbar holds the title (**Personas**), the **Demo fleet** / **Stylised illustration** badges, the two view tabs and the scale control (10 / 30 / 99 agents); everything below it is the stage, edge to edge (the view is full-bleed, and with no level-2 menu open the stage gets the full width beside the rail).

Every view's top level (L0) has the same frame: the agents own the whole field, and all text sits in thin edges around them: a **top strip** (how many need you, working / resting / off counts, usage meters, clock, key hints), a **right rail** (on the Board, first the **host card**, then everyone who needs you, most urgent first; hovering a row lights the agent in the field, selecting it opens the agent), and a **bottom strip** (newest events, system processes). Hovering or focusing an agent floats a card next to it instead of reserving space.

**The machine (Board).** The page manages the PC the agents run on, so the Board always says which machine it shows and how it is doing. The host card at the top of the rail names it (**Studio PC**, the same demo desktop as the phone layout), says **Online** with the heartbeat ("synced 2s ago", every simulation tick is a sync pass) and the round trip of its last report, draws **run slots** one cell per slot (running of capacity: 5 / 8 / 24 for 10 / 30 / 99 agents) with the queue and paused count under them, and CPU and memory. `?desktop=offline` (the phone's switch, also through `/demo?desktop=offline`) takes the machine away: the card says **Offline · Last seen 7m ago**, CPU and memory read "not reported" (a load nobody reported is not shown as a number), a band above the field says you are looking at the last state it reported, the field is desaturated and stands still (the simulation does not tick), the clock reads "as of 14:13 UTC" and the bottom strip says **Offline** instead of **Live**.

**Remote control (Board).** Nothing you do on the Board changes the fleet directly: every action is a command to the machine, and the board changes when the machine has done it. A command reads **Sending to Studio PC** while it travels (450 ms), **Studio PC is on it** once the machine has picked it up (750 ms more), and then the simulation applies it; while it is in flight its agent's tile carries a small spinning ring by the callsign, the hover card says what is in flight, and the agent's controls wait. The agent scene has **Pause** / **Resume**, **Run now** (only when it can start; it queues when every slot is busy) and **Cancel run** (only while a run is in progress; the freed slot goes to the next queued agent). Pause stops new runs, schedules and triggers; a run in progress finishes, so a paused agent stays lit (working, with a two-bar pause mark and "Pausing 45%") until that run ends and then reads off. **Approve** and **Send back** are held for a 4 s Undo window first (the review card shows "Approved · Sends in a moment" with Undo and a draining bar; the toast carries Undo too); an undone verdict never leaves the browser. The host card's **Pause all** opens a dialog that counts what it will do before you pull it (runs in progress finish first, queued runs will not start, no schedule or trigger fires, who is already off and stays off) with an option to **also stop the runs in progress now**; once pulled, the card shows **Fleet paused** and **Resume N**, which brings back exactly the agents Pause all switched off (not the ones that were off before). Fleet decisions land in the log as **Fleet** events. Offline, every control is disabled and says why.

**Find and focus (Board).** At the fleet level the top strip's pile legend is a set of toggles (**23 need you**, **21 working**, **44 resting**, **11 off**; any mix) and next to it a search box (`/` jumps there from anywhere on the board). Every word typed must appear in the agent's callsign, name, team, task or state. What does not match recedes in place instead of disappearing (tiles keep their positions, so the field's layout stays familiar), bays say how many of theirs match ("2 of 11") and a bay with none dims, the pile bar dims the piles not shown, the count reads "2 matches" or "No agent matches", **Enter** opens the first match, **Escape** clears and then leaves, and × clears search and piles. The search also narrows the Needs-you rail (its count reads "2 of 23", and a narrowed rail with nobody in it says none of the agents you found needs you, never that nobody needs you); pile toggles leave the rail alone.

**Command palette (Board).** **⌘K** / **Ctrl+K** (or **Commands** in the top strip) opens one box that reaches everything by typing: actions (go to the next agent that needs you, Pause all or Resume N, show only one pile, clear filters), every agent (those that need you first, with team and state and a state dot), every team (with its counts), and the view (Night shift, 10 / 30 / 99 agents). Starting with a verb (**pause**, **resume**, **run**, **cancel**; three letters are enough) turns the agent results into that command, offered only where it applies (cancel only for running agents, resume only for paused ones, nothing while the machine is offline): `pause ir01` Enter pauses IR01 through the same command plane as its button. ↑ ↓ move, Enter runs, Esc closes.

**Triage (Board).** **Triage** in the Needs-you rail's header, `T` at the fleet or team level, or the palette starts a focused pass over every decision waiting on you, one at a time. The queue is decisions, not agents (a failure, a question, a draft with no review of its own, and each review, most severe first, under the needs-you order) and its order is frozen when triage starts: new needs join at the end and items that resolved themselves drop out. Each card has what that decision needs and nothing else: a failure shows how the run ended (the last lines of its log) with **Retry run** (R) and **Pause agent** (P); a question shows what it asked, four quick answers (1-4 fill the field, Enter sends, Shift+Enter is a new line) and **Send and resume**; a review or draft shows its title with **Approve** (A) and **Send back** (B) (**Approve and publish** / **Send back to revise** for a draft). **Skip** (S or →), **Open console** (C), **Done** (Esc). The header counts progress, decided and skipped; the side lists what is up next. It ends on what you did and how many decisions still wait (with a button to go through them), or **All clear** when nobody needs you. Answers carry their words into the log ("You answered: “Use the safer option”"). The agent console shows the same answer box at the top of its right column while the agent waits for input (its run card's **Answer and resume** jumps there), and a draft with no review of its own now has **Approve and publish** / **Send back to revise** on its run card (it used to point at a review that was not there).

**List layout (Board).** The top strip's **Field / List** switch (or `L` at the fleet level) shows the same fleet as a table: one row per agent with its callsign and name, team (click to search for that team), state (dot, pause mark, in-flight ring), what it is doing now (progress bar and task, or why it needs you), runs today, success, cost today and its last 12 results. Columns sort (State sorts by who needs you, then what is working, furthest along first; numbers start biggest first) and the search and pile toggles filter rows. Checkboxes select (shift-click selects a range, the header box selects all shown) and a bar of bulk actions appears: **Pause N**, **Resume N**, **Run N now**, **Cancel N runs**, each counting only the selected agents it applies to, each sending one command per agent with one toast. Rows open the agent's console; the list keeps its sort and selection behind it. To fit the strip, the pile bar gives way to the pile toggles at the fleet level, the usage meters show from 1500 px and the key hints from 1700 px.

**Activity, alerts and the tab (Board).** The bottom strip's **Live · Activity** button (or `E`) opens the log as a drawer over the lower half of the field, with filters (**All**, **Needs you**: failures and review requests, **Your decisions**, **Messages**, **Runs**) and **Commands**: the audit trail of everything sent to the machine this session, newest first, each with its sim time, what it did, its target (or every agent) and where it is (Held for Undo, Sending, Received, Done, Undone, never sent). A callsign opens that agent. When an agent newly needs you (a fresh failure, mostly), a **Just in** card appears in the field's corner with **Open**; up to three stack, each leaves after 8 s, and the bell next to Activity mutes them (nothing alerts on load, offline, or behind a scene). While the Board is shown the browser tab reads "(23) Personas ...", so a background tab still says how many need you.

Both draw one state language, so a fleet of 100 sorts itself at a glance:
- **needs you** (failed, waiting for input, draft ready, or a pending review) is the loudest thing on screen: solid amber, red for failures and critical reviews (with a slight top-left light for depth), with a glyph for why (`!` failed, `?` waiting, a pen for a draft, a flag with the count for reviews, so a bare number never reads as another mark);
- **working** is lit in the brand colour and moves (progress fills, rising light, a persona typing);
- **resting** (queued or idle) is present but dim;
- **off** is hatched, shuttered or a covered desk.

On the Board a tile that changes pile flashes once (a ring and a wash in its own colour that fade over 1.2 s; none under reduced motion), so a change is not missed. Tall medium tiles (30 agents on a large screen) show what a working, waiting or queued agent is doing; resting and off tiles stay quiet. In light themes the tiles become paper: resting is a plain card, working a card tinted by the brand with a clean fill (the dark-theme mix turned muddy grey on a light ground).

- **Board.** Nine team bays fill the field, tiles ordered needs → working → resting → off inside each bay. Tile content grows with the room it has: callsign + glyph at 99, + state and name at 30, + emblem and task at 10. Clicking a bay opens the team (L1); opening an agent shows its **console**: a top bar with the emblem, callsign, name, team, state and health, today's numbers (runs, success, cost; from 1400 px) and the remote controls, with ‹ › (or `J` / `K`) stepping to the neighbouring agent (its team's order when a team is open, the field's reading order otherwise); below it three columns: the run (ring, facts, stylised trace, Retry / Answer, the last run when it rests, **What starts it**: its schedule with the next slot and its trigger, or "Paused: no schedule or trigger fires"; this block yields on short screens, the last 12 results and 24 h runs), the activity (tabs **Live log**: the current run's tool calls as a stylised terminal, newest at the bottom, grouped under phase dividers, ending on the failure or the pause; **Runs**: the last 12 runs with result, end time, duration and cost, today's runs after midnight and older ones before; **Events**: what touched it), and the decisions and inbox.
- **Night shift** (showcase, no drill-down). One building per team, one window per agent, drawn to the field's real size with the roof line near the top; a thin sky band with the moon. Needs and working windows carry their callsign; every window that needs you sends a beam to a beacon on its roof. Clicking a window, a building or a rail row pins its card (click the sky or street, or Esc, to unpin). In light themes the night becomes dusk.

Both views run a seeded simulation (runs progress and complete, failures self-heal or appear; on the Board your decisions land in the log). Escape goes back exactly one level; every agent is reachable from the keyboard. On the Board: `⌘K` / `Ctrl+K` the command palette, `/` find, `N` the next agent that needs you, `T` triage, `L` field or list, `E` the activity log, `J` / `K` the neighbouring agent in the console, `?` (or the top strip's **?**) the full map of keys, including triage's own (A, B, R, P, 1-4, Enter, S, C).

**On a phone** (below 768 px) the view is agent management instead of the stage (PLAN M13, a phone layout of this view, not a new route): a reachability banner, then one row per persona with its glyph, name, state (**Running** while a run is queued or running, **Paused** when switched off, **Last run failed**, or **Idle**; a paused persona whose run pause did not stop reads "Paused, a run is still going"), a 44 px **Pause / Resume** button, a 44 px overflow (**Run...** opens a prompt and sends the run; **Cancel run**, only while a run is live, stops the newest one), and the chip of its latest command (**Sending... -> Working... -> Done**, or Failed / Refused with the desktop's reason, "Already handled" for a command the desktop refused as a replay, or "Your computer didn't answer"). Tapping a row opens its detail sheet: **Activity** lists the last 10 runs (status, started, duration, cost when there is one) and moves live as a run progresses; **Chat** is the persona's chat (see *Chat on the phone* below). Above the personas a pinned **Athena** row opens Athena's chat in its own sheet. The banner follows the online gate: **offline** (a desktop has synced but its heartbeat is over 120 s old) disables every action (Pause, Run, Cancel; the detail sheet still opens) and says "Personas isn't running on {device}, last seen {ago}" with no download CTA; **never synced** offers "Send the download to my computer" and no actions; **online but unpaired** points at pairing in Settings; **online** shows nothing. In demo a simulated computer answers (claim at 1.2 s, done at 2.0 s; a run's execution is queued at 2 s, running at 3 s and completed at 10 s, so the row reads Running then Idle and Activity gains the run) and no download CTA shows (the demo is a tour, owner 2026-10-06); `/demo?desktop=offline` and `/demo?desktop=never` switch the simulated computer off or away for review and e2e.

## How it works
**Phone layout (phase 2, E2E-1).** `index.tsx` picks `phone/PhonePersonas.tsx` when `useIsMobile()` (max-width 767 px) and the unchanged stage (`PersonasStage`) otherwise; the view is client-only, so the media query cannot mismatch a server render. `PhonePersonas` reads `personaStore` (demo: `mockApi`'s five personas; live: `synced_personas`), never `fleet.json`. `PhonePersonaRow.tsx` gates its Pause/Resume and overflow buttons on `useSyncReachability().tierFor(persona.deviceId)` (the tier of the desktop that owns the persona) and on no open command, and derives its state with `derivePersonaRow` (`src/lib/commands/personaRow.ts`, pure, unit-tested) from `displayEnabled(persona, latest)` (the command's reported result until the synced persona is written after the command, then the mirror) and the persona's runs in `executionStore` (`personaRuns`, newest first); a completed cancel stops its run reading as live before the mirror catches up (`reportedCancelledId`). Actions go through the `api` proxy (`phone/personaActions.ts`): `pausePersona` / `resumePersona` / `executePersona` (`{ prompt }`, `runParams`: trimmed, 1-8000 chars) / `cancelExecution` (`{ executionId }`), which on the demo and supabase planes call `commandStore.send` through `src/lib/commands/personaCommands.ts` (loaded lazily, because the store reaches `api` through `personaStore`) and answer `{ commandId }`. `PersonaActionsSheet.tsx` (the menu, then the Run prompt in the same sheet; a note when the live run is older than the 24 h execution re-read window, spec 1.2) and `PersonaDetailSheet.tsx` (tabs, Activity, the marked Chat slot) reuse `primitives/BottomSheet.tsx`, whose slide and fade are off under reduced motion. `PhonePersonas` owns which sheet is open and fetches personas and executions on mount; the demo plane re-reads executions after each fixture write (`onFixtureChange`). `ReachabilityNotice.tsx` renders the tier banner (download via `mobile-landing/shared/handoff.ts`: share sheet, else clipboard), `CommandChip.tsx` the six states. Copy: `mobileCopy.personas` (row states, overflow, Run sheet, Activity), `mobileCopy.reach`, `mobileCopy.command` (English-only pending, `src/i18n/pending/mobile.ts`); Activity status labels reuse the translated `t.dashboardUi.status` through `StatusBadge`. Contract: `docs/concepts/mobile-revival/PHASE2-SPEC.md` §2.2, §4.3, §6.2, §6.3.

**Directing an App Master from the phone (weekend item E).** The detail sheet's third tab, **Direct** (`phone/DirectMasterPanel.tsx`), sends a `channel_say` command (`api.sayToMaster` -> `commandStore`; params exactly `{message}`, `persona_id` and the envelope's persona = the App Master, `target_device_id` = the persona's own device). The desk writes the text as the operator's message in that master's channel and starts no run, so this is **not a chat**: nothing comes back here, and the headless App Master reads it at its next wake. The web has no synced App Master marker, so the tab is offered on every persona and the desk decides (`not_app_master`: only the App Master a headless loop reads takes directions, i.e. a persona holding a non-retired project-bound charter that is the newest `App Master%` persona with a charter bound there; `rate_limited`: a paired phone may make at most 10 says in any 10 minutes, counted by the desk from the database across all personas, and a say approved at the desk is not capped). A phone's row carries `author_id` = the controller id and `author_label` `phone: <name>`, and the desk clears the cloud row's `params` and `envelope` on every terminal write. Limits (`src/lib/commands/channelSay.ts`, pure): the text is trimmed, then counted by Unicode code point (`Array.from`, as the desk's `chars().count()`); 1 to `SAY_MAX_CHARS` = 2000 is allowed, empty or longer is refused before sending and never cut (the field shows a live `n of 2000`, and Send is disabled when empty or over). The phone then masks credential-looking tokens with the desk's rules before signing (`src/lib/commands/redactText.ts`, the port at `dccf5776`, checked against the shared fixture `fixtures/redact-text-v2.json` copied from personas `4dcd9f18b4`), so a pasted key never reaches the cloud row; the desk masks again on arrival. The 2000 bound applies to the typed text and again to the masked text, because masking can lengthen a short value (`DB_PASSWORD=hunter2` becomes `DB_PASSWORD=[redacted]`); either over the bound throws `message_too_long`. The refusal's words explain that hiding keys as `[redacted]` lengthened the direction, because the counter shows the typed length. The desk's `redact_text` keeps a value that is already `[redacted]` (personas `8fe3fbfb76`), and so does the port, so a direction masked on the phone is stored as sent. Gate: the same as the other signed verbs (`actionsEnabled`, judged on the persona's device; disabled with a reason offline, unpaired, never synced, on the desktop data plane (`channelSay` in `DESKTOP_UNSUPPORTED_ACTIONS`), or when the persona has no device; the demo needs none), and Send waits while a say is open. Progress is `CommandChip`; a completed command reads as **Delivered** (`channelSayOutcome`: `changed: false`, a re-delivery that wrote nothing, also means delivered), and each refusal token (`bad_params`, `empty_message`, `message_too_long`, `not_found`, `not_app_master`, `rate_limited`, `internal_error`, `controller_not_paired`, `controller_revoked`, expiry) has its own words in the say-specific `mobileCopy.say.errors` (not the chat block, whose limit is 8 KB). The persona row ignores a say (`latestForPersona` skips `channel_say`), so it neither shows a chip there nor holds Pause. Demo: `mockCommandPlane` completes it at 2 s with `messageId` = the command id, `changed: false` for a repeated id, and `rate_limited` for a new id once 10 says were delivered in the last 10 minutes (no `not_app_master`: the demo has no App Master marker). The web reads back only `id`, `status`, `result` and `error_message` (the poll and the Realtime handler in `useSyncedRealtime.ts`), so the cleared `params` and `envelope` change nothing it shows. Orchestrator plane: a 501. Contract: `PHASE2-SPEC.md` §2.2, personas `7653b0be85`, hardened by `2c65f9f0ea` (cap), `693fc11e77` (cleared cloud row), `78c5fcd8e6` (App Master test). Needs the `channel_say` CHECK from `scripts/setup-sync-db.sql` applied (`check-sync-schema.mjs` reports it).

**Chat on the phone (phase 2, PHASE2-SPEC §5.2, §5.3, §6.2; PLAN M18, M19).** One component, `phone/chat/ChatPanel.tsx`, serves both kinds of thread: Athena's (the pinned `AthenaRow` opens `AthenaChatSheet`, no new route) and a persona's (the detail sheet's Chat tab). It goes thread list (`ChatThreadList`: pinned first, then latest activity; **New chat**) -> transcript (`ChatTranscript`: oldest first, assistant turns through `MarkdownReport`) -> composer (`ChatComposer`). Reading is open to every tier; the composer is enabled only where actions are (`actionsEnabled`: online + paired, or the demo), judged on the desktop that holds the thread (a paused persona still chats, PLAN M21: pause stops its triggers, schedules and subscriptions, not an explicit ask); otherwise it is disabled with the tier's reason (`composerDisabledReason`). Sending is a `chat_send` command (`api.sendChatMessage` -> `commandStore`, params `{sessionId | null, message}`, `persona_id` = the persona or `'athena'`); the desktop completes it when the turn *starts*, and the reply arrives later as synced data. The phone shows the message at once as an optimistic bubble, then the turn's state under it: **Sending...** while the command is open, **"{name} is thinking..."** once it completed (persona chat follows the run named by `result.executionId` in `executionStore`), the desktop's refusal with **Retry** / **Dismiss** (`chatErrorKind` maps the tokens `chat_sync_off`, `athena_off`, `empty_message`, `message_too_long`, `bad_params`, `not_found`, `controller_not_paired`/`controller_revoked`, `unsupported_command_type` -> "Update Personas on your computer to chat from your phone", `replayed` -> "Already handled. Your computer will not run the same command twice.", and expiry), or **"No reply. The run failed."** with Retry when the run ends otherwise than completed; after 5 minutes without a reply it says the reply will show once synced. The merge is pure and unit-tested (`src/lib/chat/chatModel.ts`, `deriveTranscript`): a send's bubble gives way to the synced user message the command's `userMessageId` names (or, when it names none, the oldest unclaimed user message with the same text written no earlier than the send), and its turn ends at the reply (the assistant message of `executionId`, or any assistant message after the user message). A **New chat** draft follows the thread its command reports (`result.sessionId`). Chat sync is a desktop opt-in, off by default (M19), so an empty thread list explains how to turn on **Sync chats**. The sheets are `keyboardSafe` (`BottomSheet` sits on the on-screen keyboard via `useKeyboardInset`, a `visualViewport` reading), targets are 44 px, and spinners are `motion-safe`. Data: `chatStore` (threads by kind and persona, transcripts by `(kind, device, session)`, this tab's sends) reads `api.listChatSessions` / `listChatMessages` (demo: `mockApi` over `MOCK_CHAT_SESSIONS` / `MOCK_CHAT_MESSAGES` in `mock-dashboard-data.ts`, Athena plus two personas; live: `synced_chat_sessions` / `synced_chat_messages`, newest 200 messages per thread; orchestrator: empty, and sending is a 501). Realtime: both chat tables are watched in `useSyncedRealtime` and re-read only the open chat (`refreshOpen`); a completed `chat_send` re-reads it too. In demo the scripted desktop answers (`mockCommandPlane`: the user message is written when the command completes at 2 s, a persona turn is a run queued at 2 s, running at 2.5 s, completed at 3.8 s, and the canned reply lands at 4 s; every write persists for the session). Copy: `mobileCopy.chat` (English-only pending, `src/i18n/pending/mobile.ts`). **Desktop data plane (`NEXT_PUBLIC_DATA_SOURCE=desktop`).** The health probe alone says `online`, but the desktop's local API does not serve pause, resume, chat send or a review verdict; `DESKTOP_UNSUPPORTED_ACTIONS` (`src/lib/sync/desktopUnsupported.ts`, pinned to `desktopApi` and `desktopShapes` by its test) names them, and the gates read it (`desktopUnsupported`), so these controls are disabled before the click with a reason (`mobileCopy.reach.desktopUnsupported`) and no request is sent.

**View and shell.** `src/components/dashboard/views/personas/index.tsx` is the view the dashboard SPA renders for `personas` (the default view: `/dashboard` and the demo entry land here); `spa/views.ts` marks it `fullBleed`. The shell owns the view and the scale; the stage is `calc(100dvh - 4.25rem)` minus the 48px toolbar, with a 700px floor. Each fleet view is a `next/dynamic({ ssr: false })` chunk, so the 130 KB fleet JSON and the art never reach the dashboard's first load. The view is kept alive across view switches (`spa/ViewOutlet.tsx`): leaving pauses the simulation (its effects unmount) and keeps the chosen view and scale.

**Shared L0 pieces.** `FleetFrame.tsx` (the top / main / rail / bottom grid), `attention.ts` (`attentionOf`, `needsTone`, `ATTENTION_COLOR`, `countAttention`: the one state language, colours from site tokens only), `NeedsYouRail.tsx` (the ranked rail). ## Conventions & gotchas
- Demo data, not a live fleet: the simulation, the decisions and the fleet are synthetic by design and labelled so (Demo fleet badge). Wiring it to `usePersonaStore` / synced executions is the next step for a real tenant.
- All colour is from site tokens; state and severity text is mixed toward `--foreground` in light themes to hold contrast. "Working" uses `--brand-cyan`, so it takes each theme's brand colour (purple in dark-purple, green in dark-matrix).
- Motion is gated by `useStillMotion` (reduced motion: crossfades and stillness) and `usePageVisibility` (loops and simulation stop on a hidden tab). Under reduced motion the simulation still updates data.
- The fleet stage is desktop-only, like the contest brief, and keeps a 700px minimum height; phones get the persona list instead (2026-10-06). The two show different populations in demo (the stage's 99-agent `fleet.json` vs `mockApi`'s 5 personas): spec open question 5.
- Phone layout, still deferred: the "Out of sync, check the desktop" notice 30 s after a disagreeing mirror.
- Chat: no token streaming on the phone (spec 5.3): the reply lands whole, 2-5 s after its run ends. A `chat_send` is not a row command: `latestForPersona` skips it, so a chat neither shows on the row's chip nor holds Pause. Persona chat needs a desktop with the persona `chat_send` handler; an older one refuses with `unsupported_command_type`, shown as "Update Personas on your computer to chat from your phone". Retry sends a new command with the same text (into the thread the first one reported); the old bubble goes. Sends live only in this tab's memory: a reload drops an unsynced bubble (the desktop still has the message if its command completed).
- Assistant text is untrusted (it can quote what a persona read through its connectors): `MarkdownReport` renders React elements only and filters link schemes (`markdown-report/safeHref.ts`). Row-state precedence is Paused > Running > Failed > Idle, so the Pause button always reads back.
- Until the runs first load (`executionStore.executionsFetchedAt`), a row claims only Paused; its state line is blank (`data-persona-state="loading"`) rather than a premature Idle.
- Row states and Activity read `executionStore`'s newest 50 runs overall, not a per-persona query: a persona whose runs are all older shows none.
- On the supabase plane a run from the phone is a signed command that runs without desktop approval for a paired browser (spec D1); the web no longer sends the legacy unsigned `run_persona` insert (the desktop's approval card).
- Board's `N` and Escape listen on the document while the Board is mounted (ignored in inputs, with modifiers, and while a modal dialog is open).
- `attentionOf` puts running before off: a paused agent finishing its last run is working, not off (the Night view's store never pauses, so it is unaffected).
- The console's live log, run history and schedule are stylised demo data drawn from the fleet's counts (labelled "Tool calls: stylised illustration" from 1500 px, and by the toolbar's Stylised illustration badge); a live tenant would read executions and the persona's triggers instead.
- Variant 1's Timeline and Map views and each variant's own header and scale control were not ported. Variant 2's Office (an office-floor L0, team cutaway and agent room) was built and then descoped: it added no clarity the Board does not give.
