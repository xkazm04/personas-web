# Localized Guide Content (14 locales)
> Hand-translated guide topics + per-module articles for the 13 non-English locales, mirroring the English guide-data shape, served as whole units: a current translation, or the whole current English page with the older translation one tap away. · **Route:** n/a (data layer) · **Status:** Translations (13 non-en locales)

## What it does
The `/guide/*` section ships its long-form help content (topic titles, descriptions, and article bodies) in 14 languages. English is the source of truth under `src/data/guide/`; the 13 non-English locales (`ar`, `bn`, `cs`, `de`, `es`, `fr`, `hi`, `id`, `ja`, `ko`, `ru`, `vi`, `zh`) each carry a hand-translated mirror under `src/data/guide/locales/<lang>/`. A single resolver, `resolveTopicUnit`, serves each topic as **one whole unit**: the locale's title, description and body together when that translation is current, or the whole current English page when it is not. A reader never gets a translated title over an English body, and never gets an out-of-date translation presented as current.

When a translation predates the current English (24 of 116 topics per locale on 2026-09-23, plus 1 translated-but-unrecorded topic whose English changed since: 25 per locale), the reader sees the current English page under a one-line notice in their language ("This page was updated in English after it was translated.") with a single button to read the older translation, and the same button to come back.

This is still **dormant in production**: the language switcher is gated (`LANGUAGE_SWITCHER_ENABLED`, `src/stores/i18nStore.ts:41`, dev/QA only), so production readers take the `lang === "en"` path, which loads no locale module and no status table.

## How it works
- The guide topic page renders English on the server (no locale signal in URL/cookie today), passing the English `content` body into `TopicView` as a prop. The English SSR output is unchanged by the whole-unit policy.
- On the client, `TopicView` reads `language` from `useI18nStore`. When it is not `en`, a `useEffect` calls `resolveTopicUnit(language, topic.id, englishUnit, { prefer })` and swaps the resolved unit into local state (`TopicView.tsx:79-89`). A render-time prev-state reset (`TopicView.tsx:55-61`) restores English and clears `prefer` on any locale/topic change, satisfying React 19's no-setState-in-effect rule.
- `resolveTopicUnit` (`getLocalized.ts:125`) returns `{ title, description, body, unit, status, alternate }`:
  | Situation | `unit` | `status` | `alternate` |
  | --- | --- | --- | --- |
  | `lang === "en"` (no loader or table touched) | `canonical` | `source` | `null` |
  | locale lacks the title, description or body | `canonical` | `absent` | `null` (no dead button) |
  | whole unit present, not in the status table | `translated` | `fresh` | `null` |
  | whole unit present, table says `stale` / `unverified` | `canonical` | `stale` / `unverified` | `translation` |
  | same, with `prefer: "translation"` (the reader's tap) | `translated` | `stale` / `unverified` | `canonical` |
- The status table is `src/data/guide/translation-status.ts`, generated by `scripts/i18n/emit-guide-status.mjs` from the history-anchored drift classifier (see below), so an instrument-only difference (line endings, the old extractor) never demotes a correct translation. Mapping: `stale/content` -> `stale`; `stale/unverified` -> `unverified`; `missing/present-unpinned` whose English changed since the key landed -> `stale`; `missing/present-unpinned` whose English is unchanged -> not listed (served translated: those 18 topics per locale are translated, just never stamped); `present-unpinned` with no anchor -> `unverified`.
- `TopicView` renders `TranslationNotice` (`src/components/guide/TranslationNotice.tsx`) whenever the resolution has an `alternate`. The toggle only flips `prefer`; the notice markup is identical in both states, so focus stays on the button. The `<article>` gets `lang="en"` while the English unit is shown to a non-en reader, and the locale code while the translation is shown.
- Locale modules and the status table are loaded lazily via dynamic `import()`; the locale modules are memoized in module-level registries (`getLocalized.ts:68-111`). A failed import (missing locale dir or category file) is swallowed and returns `null`, which resolves to the whole English unit (`absent`). All three loads run in parallel and are injectable (`opts.loaders`) for tests.
- Category name/description are **not** in this folder; they live in `src/i18n/<lang>.ts` under `guide.categories` / `guide.categoryDescriptions` and are resolved by the synchronous `getLocalizedCategoryFromI18n` helper (`getLocalized.ts:176`). The notice strings live there too, under `guide.translationNotice`.

## Translation freshness (drift detector)
The runtime never reads `_meta.json` or git: it reads the generated `translation-status.ts`, which `emit-guide-status.mjs` derives from the same classifier. `check-guide-translations.mjs` (a thin CLI) runs `classifyGuide` from `scripts/i18n/guide-drift.mjs`:
- A pin byte-equal to today's hash is `fresh / exact` and needs no history.
- Any other pin is **anchored**: the classifier walks the English guide revisions (`src/data/guide/content`, `topics.ts`) committed at or before the pin's `translatedAt`, newest first (at most 16), and recomputes the pin at each under the closed variant set {scanner, legacy regex} x {CRLF, LF}. The first byte-equal match is the English the translator saw.
- It then compares the **normalised** unit (title, description, full body, LF) at the anchor with the working tree: equal -> `fresh / instrument:eol` or `instrument:extractor`; different -> `stale / content`, carrying both hashes, the anchor revision and a line diff. A pin no variant reproduces is `stale / unverified`, never fresh.
- A topic with no pin whose body the locale carries is `missing / present-unpinned`, anchored to the commit that added the key to the locale file; `missing / absent` means no body at all.
- `--strict` exits 1 on any stale or missing and 0 when the only differences are `instrument:*`. Missing history (shallow clone, no git) exits **3** with "history unavailable" and prints no numbers. Usage errors exit 2.
- `--work-order` groups content-stale topics (and present-unpinned topics whose English changed since they landed) across locales with the English diff. The translator prompt's `refresh` mode consumes it.
- Measured 2026-09-23: the old bare-hash comparison reported 871 issues (13 x (48 stale + 19 missing)). The classifier reports 559: per locale, 24 content-stale, 19 present-unpinned (1 of them with English changed since, `companion` category), 49 exact, and 24 instrument (16 EOL: `memories.ts` and `troubleshooting.ts` are LF on the Windows checkout; 8 from the 071c13d extractor fix) folded into fresh. All 97 pins verify at `5cfc87d`; 0 unverified.
- No pin is rewritten by any of this. The CRLF hash definition in `guide-source.mjs` stands, and so does CI's decision not to run the detector (CI clones are shallow; wiring it needs `fetch-depth: 0`).

## The status table contract (regenerate after English edits)
- `node scripts/i18n/emit-guide-status.mjs` writes `src/data/guide/translation-status.ts` (only when it changed; keys sorted, no timestamp, so the output is deterministic). `--check` exits 1 when it is out of date. Without full git history it exits **3** and writes nothing; with no English read it exits 2 and writes nothing. A table can never silently become empty or all-fresh.
- `getLocalized.test.ts` holds the contract, in two parts: (1) always, even on a shallow clone: `GUIDE_STATUS_INPUT_DIGEST` must equal the digest recomputed from the working tree (every English unit EOL-normalised, every `_meta.json` pin, every locale's body-key set); (2) with full history: the table must deep-equal the one the classifier derives today (about 20 s on this tree; skipped on a shallow clone).
- Consequence (policy-tighten): **any English guide edit (title, description or body), `_meta.json` change or added/removed locale body fails `npm run test:unit` until the table is regenerated.** That is deliberate: an English rewrite changes which translations are current, so what a localized reader is served must be re-decided in the same change.
- Measured 2026-09-23: 25 topics per locale are listed as `stale` (the 24 content-stale + `athenas-long-term-memory`), 0 `unverified`; the other 18 present-unpinned topics are served translated.

## Data & state
- **Source:** static TS modules — `src/data/guide/locales/<lang>/{topics,content/*}.ts`, mirroring `src/data/guide/{topics,content/*}.ts`. Bodies are raw markdown-ish strings (custom `:::steps`, `:::info`, `:::tip`, `:::compare`, `:::cards`, `:::diagram`, `:::usecases` directives parsed by `GuideMarkdown`).
- **Stores:** `useI18nStore` (`@/stores/i18nStore`) supplies `language` (switcher gated to dev/QA). No store owns the resolved unit or the reader's `prefer` — both live in `TopicView` local `useState` and reset on locale/topic change.
- **API routes:** none. Pure data layer resolved client-side via dynamic `import()`.
- **Types:** `TopicUnit { title; description; body }`, `TopicUnitResolution` (+ `unit`, `status`, `alternate`), `TopicUnitStatus`, `TopicUnitPreference`, `TopicUnitLoaders` (`getLocalized.ts:32-63`); `GuideTranslationStatus` / `GuideTranslationStatusTable` (`translation-status.ts`); `Language` from `@/stores/i18nStore`; `GuideTopic` / `GuideCategory` from `@/data/guide/types`.

## Integration points
- **i18nStore** — gates the whole feature; `resolveTopicUnit` returns English without loading anything while `language === "en"`. The translations are inert until the locale switcher ships.
- **TopicView** (`src/app/guide/[category]/[topic]/TopicView.tsx`) — sole caller; also derives headings/reading-time from the resolved `body`, so a locale swap re-parses the TOC.
- **Category strings** flow through `src/i18n/<lang>.ts` (the UI bundle), not this folder — two parallel localization systems meet on the guide page.
- **GuideMarkdown** renders the resolved body; locale strings must use the same custom directive syntax as English or they render as literal text.
- **`GUIDE_TOPICS` is the key universe** — a topic added there with no matching locale key is served as the whole English unit (`absent`, no notice); no error. Adding it still changes the table's inputs, so regenerate.

## Conventions & gotchas
- **Whole units, not per-field fallback (changed 2026-09-23).** Until then the resolver fell back per field, documented as intentional: a translated title could sit over an English body, and a stale translation was served as current. That design was reversed as an owner-approved content call: stale topics show the whole current English with a notice and one tap back to the older translation; a locale missing any one of title, description or body serves the whole English unit with no toggle. See the registry's translation-pipeline-topology / canonical-fallback-serving ("never splice").
- **Translated-but-unrecorded topics are served translated.** 19 topics per locale landed on 2026-06-14 without a `_meta.json` pin. The classifier anchors them to the commit that added them; 18 have unchanged English since and are served translated, `athenas-long-term-memory` changed and is `stale`. A future pin for them changes nothing at runtime unless the verdict changes.
- **No `_registry.ts` exists.** The mechanism is the template-literal dynamic `import()` at `getLocalized.ts:80` and `:98`.
- **Bodies can be out of sync with English even though keys match.** Counts line up — each locale now has 116 topic keys and 12 `getting-started` content keys, matching English — but key parity does **not** imply prose freshness. Example: English `content/getting-started.ts` describes a **Windows-only** product with a **"Precondition: Install Claude Code"** section and a `:::cards` platform-availability block (`content/getting-started.ts:2-37`); the DE and JA `installing-personas` bodies still describe **Windows/macOS/Linux all available** with **no Claude Code precondition** (`locales/de/content/getting-started.ts:2-24`, `locales/ja/content/getting-started.ts:2-24`). So shape-sync (enforced by `tsc` / key parity) does **not** imply content-sync. Re-translating after English edits is still a manual step, but it is no longer unguided: `npm run check:guide-translations -- --work-order` lists every topic whose English changed since its translation (`installing-personas` among the 24), with the English diff, and `--strict` fails on it. Nothing wires the check into pre-push or CI yet. Readers are protected meanwhile: those topics are served as current English (with the older translation one tap away), not as the outdated translation. After re-translating and re-pinning, regenerate the status table.
- **Hand-translation is required.** Per project rules and MEMORY, every non-en string must be hand-translated — no English placeholders. The samples confirm this (DE/JA are fully localized, including the custom directive labels and Anthropic/Claude/OpenAI proper nouns left as brand names).
- **Locale files are mojibake on disk.** Non-en `src/i18n/*.ts` are UTF-8+BOM with double-encoded values; the same caution applies when editing these guide locale files — anchor edits on pure-ASCII keys (the topic IDs and directive markers), write correct UTF-8, and don't attempt to "fix" existing encoding.
- **`description?` and `title?` are optional in the topics type** (`getLocalized.ts:52`), but a locale that carries only one of the pair has no whole unit and is served in English.
- **Failed imports are silent.** A typo'd category filename or a missing locale dir yields `null` and a whole-English render (`absent`, no notice) with no console warning — easy to miss a whole untranslated category.
- **The notice is client-only and has no motion.** It appears after the async resolution on a non-en locale, never in the English SSR output. Its markup is the same in both states; only the button label changes.
- **Category set is 11** (`getting-started`, `companion`, `agents-prompts`, `credentials`, `triggers`, `pipelines`, `memories`, `monitoring`, `testing`, `deployment`, `troubleshooting`). All 13 locales are complete on file presence — every locale has `topics.ts` + all 11 content files (including the newest `content/companion.ts` for the Athena category). Note: the `companion` category **name/description** in the grid is not yet in `src/i18n/<lang>.ts` — it renders from the English `categories.ts` via the grid's fallback until that chrome string is translated (a small separate follow-up; the topic titles/descriptions/bodies *are* fully translated here).
